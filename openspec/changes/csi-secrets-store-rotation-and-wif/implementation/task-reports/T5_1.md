## Summary

Extended `hack/e2e.sh` with two new test functions covering US1 (rotation enable/disable, SC-001) and US3 (custom rotation interval, SC-002): `test_rotation_toggle` and `test_rotation_custom_interval`. Both are wired into the script's execution sequence immediately after `test_pod_with_secret`, following the existing fail-fast `test_pods_dump` → `test_teardown` → `exit 1` pattern used by every other stage.

Since this repo's `e2e-provider` has no existing mechanism to mutate the secret *value* it returns mid-test (confirmed via investigation — zero rotation/versioning scaffolding exists today), the tests instead drive and verify the operator's own reconciliation surface for this feature: patching `ClusterCSIDriver.spec.driverConfig.secretsStore.secretRotation` and confirming the `secrets-store-csi-driver-node` DaemonSet's `csi-driver` container args (`--enable-secret-rotation=`, `--rotation-poll-interval=`) converge to the expected values. This matches the "Manual/Cluster" verification row documented in `plan.md` §6 for this feature and is the correct scope for what is testable end-to-end without a provider-value mutation test double.

## Deviations

Scoped verification to the operator's own reconciliation surface (DaemonSet args) rather than the driver's actual runtime refresh behavior, because this repo's `e2e-provider` has no mechanism today to mutate returned secret values mid-test (investigated and confirmed absent — no ConfigMap, env var, or versioning lever exists in this repo). Building such a provider-mutation harness was out of scope for this task's payload, which is limited to extending `hack/e2e.sh` in its existing style. This deviation is traced and justified in the task's presentation; it does not reduce coverage of what the *operator* is responsible for delivering (SC-001/SC-002 are about the driver's configured rotation behavior being propagated correctly, which this test does verify).
